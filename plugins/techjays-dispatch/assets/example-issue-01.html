§ 01Model WatchThe landscape this week

Model Watch

Benchmark // Kimi K3

Kimi is the quiet value play

The team's Kimi analysis is the win of the week. Against Fable, Kimi delivered comparable output on standard engineering tasks at roughly a third to a quarter of the cost. The takeaway wasn't “switch everything” - it was that the “one silver-bullet model” era is over.

Ashish's honest read: after three-plus weeks of daily use, he still can't reliably tell Fable 5 and Opus 4.8 apart on ordinary engineering. Fable runs slower and burns more tokens; the quality gap only shows up on genuinely ambiguous, research-flavoured problems. For the bread-and-butter, both are excellent - and cheaper options are closing in fast.

“When Fable came out it was sold as the silver bullet for everything. Then Kimi showed up. Now it just looks like a menu of good options.”- Ashish Ramaswamy

§ 02Cover StoryFiled 22.07 · Ragul Kachiappan

The Two-Reviewer Problem

Ragul spent the last fortnight running full loop engineering on a real feature: take a big module, split it into phases, split each phase into tasks, and wire in review gates, pivot gates, TDD and a brainstorming pass so the whole thing runs semi-autonomously. He only steps in at the review points.

The feature: expanding the coach-facing chat so it can query any client data - health scores, effectiveness metrics, coaching-timeline insights - not just the vector store. Proper agentic chat. Five phases, ~7 tasks each, about a week of Claude time.

Then he did something clever: he ran two reviewers on the same code - Opus (or Fable) reviewing, and Sonnet reviewing. And they saw completely different things.

loop-engineeringreview-gatesTDDagentic-chat
“Opus flagged the technical implementation problems. Sonnet flagged the product ones - ‘do you even need this? isn't this over-engineering?’”- Ragul Kachiappan
The concrete bug

A temporal query that quietly wasn't built

A coach should be able to ask “how have I done over the last 6 months?” The time-range logic was in the ADR and technically in the task list - but the implementation queried the wrong table, and current-time handling plus context-explosion cases were never covered. The happy path passed every test. The spec did not.

Opus's reviewer never raised it. Sonnet did - because it was reading against the intent, not the code.

The deeper worry

The “doc factory” problem

When a loop writes a thousand lines over four days, the human loses the mental model of what actually got built. Ragul name-checked a term doing the rounds - the “doc factory” - for exactly this: you're constrained by throughput, but how do you keep enough cognition in your own head to know it still points at the outcome you wanted?

Dharma's framing: the loop isn't “done” until the definition of done is real. Anchor every loop to explicit acceptance criteria - then the model choice matters far less.
§ 03The Review RoomRajesh · Aravind · Dharma

The Review Room

The two-reviewer finding opened a bigger thread: don't let a model grade its own homework. The pattern the room kept hitting - build with one model, review with the same model, and the review comes back soft. Build with it, then review with a different model, and you get contradictory, more useful comments.

The working hypothesis: a model is grounded in its own implementation knowledge, so its review orbits what it already “believes” the code should be, rather than genuinely re-examining it. A second model has no such attachment.

Rajesh raised the adversarial-reviewer angle: is Sonnet's product-first behaviour a system-prompt effect, or its nature? Ragul's suspicion - Claude Code's local scratch files may be polluting its own adversarial pass, while the shared workspace feeds it product memory and rules.

Consensus wisdom
Cross-model review, as a rule
  • Split the roles. One model for code-correctness, one for product-fit. Ragul's double-pass is now a template worth stealing.
  • GPT for review = shaky. Aravind & Ragul both saw GPT-family reviews post comments that were blatantly untrue about the codebase.
  • Claude review = thorough but token-hungry. Slower and pricier, but the comments are good.
  • Gemini in-IDE = weak. Not recommended for serious review passes right now.
Rule of thumb: whoever writes it shouldn't be the only one to review it.
§ 04The ToolshedAbu · Anamul · Arjun · Har

The Toolshed: Design

Discovery // Google Stitch

Design with no designer

On the Echo POC with no designer on hand, Abu used Google Stitch (Pro) to generate the UI. It works Figma-style - describe the project, get editable screens and a live preview, then export three files: the screen capture, the design assets, and clean HTML. Edit by prompt or by hand.

Native // Claude Design

Skills that think like a UX lead

Anamul and Har pointed to Claude Design and its hand-off into Claude Code. The move: install UX skill sets (the room mentioned 21st.dev-style and “UX proto” packs) so prompting inherits a real designer's mental model - it spins up a design folder and works from that knowledge base instead of round-tripping to another tool.

Craft // Arjun's method

Feed it a design system

Arjun's result: Claude Design is far better when you hand it a React design system built on atomic-design principles - tokens, colours, typography first, then templates. A one-time setup that pays off every time after.

Gotchas the room hit
What still breaks in AI design tools
  • PNGs don't work. Use SVGs. Raster images currently break Claude Design layouts.
  • Name things properly. Minimal component/slide names get reused blindly - every component needs a descriptive, explanatory name so the system understands intent.
  • Information architecture is weak. Arjun's warning: let it design freely and the pages look strange. You must spell out how the IA should be organised - agents don't do it yet.
“I tried Stitch three or four months ago and it was very bad. Now it's production quality. The tools are evolving at such a pace - when you find something good, drop it in the group.”- Arjun S

Staying in Flow

Hack // Yash

Stop the idle wait

Yash's CLAUDE.md rule: if there's even 1% doubt, stop and ask - don't assume. Quality went up, but sessions sat idle for 15–30 min waiting on him. Fix: a remote-control config + push notification to his phone, so he answers from the Claude mobile app - even mid-lunch. Claude can wire this up itself if you just ask.

Run features in parallel

Tapu's been using a terminal multiplexer (Supercode-style, Mac) to work several features at once. § 06Big IdeaBinu Babu

Experience Contracts

We already use data contracts for agent-to-agent communication. Binu's proposal: bring the same rigour to how a screen should feel. Call it an experience contract - a written spec, per feature or per product, of the user's expected behaviour and psychological reaction.

It captures things we usually leave implicit: what's the ideal time-to-action? What's a good vs. bad experience for this step? Is there an emotional beat attached - a quick, quality recall that earns a little dopamine? What mental model is the user holding?

Feeding an agent that context changes what it builds. Binu's been using it on the retail product and it's already simplifying screens - helping decide what actually belongs, instead of dumping every feature we've built onto the page just because it exists.

“The point where software meets the user - that interaction is the contract. Label how it should feel, then build features that honour it.”- Binu Babu

§ 07On the HorizonAravind Krishna M

On the Horizon

Aravind flagged WebMCP as the thing to watch. Today we hand-build a chatbot into every product. Tomorrow, a browser-native assistant (think the “ask Gemini” layer in Chrome) connects directly to the MCP tools a site exposes - no bespoke chat widget required.

If that holds, the in-site chatbot becomes a technology of the past: you expose your MCP tools, and the browser's own chat interface talks to them. Redbus and Flipkart are reportedly already MCP-ready; Chrome has rolled WebMCP out in the US; Alibaba shipped something similar; and Claude for Chrome is the same idea from the other direction.

Still experimental - but worth designing for now. The teams that expose clean MCP tools early won't need to rebuild chat later.
The shift, in one line
Old world

Every product ships its own chatbot, its own chat UI, its own glue code.

New world

Products expose MCP tools; the browser's assistant becomes the interface.

  • Redbus / Flipkart - MCP endpoints reportedly live
  • Chrome (US) - WebMCP rolled out
  • Alibaba - comparable browser assistant
  • Claude for Chrome - MCP-controlled browsing, already usable

Jetrix can't bulk-edit

Jetrix (our tracker) has no bulk upload and no way to reorder user stories - punishing when you're loading ~180 of them. Anju's workaround: grab the auth token from Chrome dev-tools and have Claude write straight into Jetrix. It worked, but it's not the way.
